Tenant Access

Single sign-on and access control for small companies that run their own tools, like Grafana, Outline and Gitea. People sign in with Google or Microsoft, admins decide who may open which app, and every sign-in and refusal is logged.

The demo needs no account. It signs you in as the owner of a sample company, read-only. The free hosting can take about 30 seconds to wake up.

The problem

A company of 5 to 50 people that hosts its own tools ends up with a separate login for each of them, and no single place to see who has access or to turn someone off. The big identity products solve this, but they are priced and built for much larger organisations.

What I built

  • Sign-in with Google or Microsoft, mapped to a company by the verified email domain
  • An OpenID Connect provider of its own, so apps like Grafana sign in through it (code flow with PKCE, RS256 tokens, JWKS)
  • Per-app access rules, an audit log with CSV export, and signed webhooks
  • Partner mode, so an outside IT firm can administer several client companies
  • Billing with Stripe, English and Norwegian UI, and a public read-only demo

Decisions worth talking about

01

Isolation the database enforces, not the code

The classic multi-tenant bug is one query that forgets WHERE tenant_id = ?. I put the rule in Postgres instead: every tenant table has row-level security, forced even for the table owner, and each request sets the tenant for its transaction. With no tenant set, reads come back empty and writes are refused.

Then I found that production was quietly skipping it. Neon's default owner role has BYPASSRLS, so every policy was ignored. The tests had not caught it because they ran as a normal role. The fix was a restricted role for the app, a separate one for migrations, and a startup check that refuses to run if the app's role can bypass the policies.

-- Every tenant table, forced even for the owner
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE users FORCE ROW LEVEL SECURITY;

CREATE POLICY users_tenant_isolation ON users
  USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);

02

Closing the nOAuth takeover

With Microsoft's multi-tenant sign-in, anyone can create a directory and give a user any email address. Trusting that address would let a stranger sign in as your colleague. Work-account emails only count when the token says the directory verified the domain, and an existing account is never linked to a new identity by email alone.

03

A public demo nobody can vandalise

Anonymous visitors get an admin seat in a sample company, so the seat has to be harmless on the server, not just in the UI. One app-wide dependency refuses every write from a demo session, the demo apps' secrets were thrown away at seed time, and visitors' IP addresses are never stored.

04

Webhooks that can't be aimed inward

Audit events queue their deliveries in the same transaction as the event, and a background sender signs them with Standard Webhooks headers and retries for about seven hours. Private and loopback addresses are refused before every send and redirects are not followed, so a webhook can't be used to probe the server's own network.

From the demo company

What I took from it

Test against the same database role production uses. A security property that only holds in CI is not a property. I also learned to keep the scope small on purpose: two roles plus an owner, one container, one origin, one cookie.

What I would do next

Automatic user provisioning (SCIM) from Google Workspace and Entra, a key rotation screen for the token signing keys, and paid hosting without the cold start once the first companies are using it.
